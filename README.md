# Echo v4.7 — A Fine-Tuned Scheduling Agent

Echo is a **Qwen3-4B** model fine-tuned with stacked LoRA adapters to act as a scheduling
assistant: it reads an incoming message, reasons about it, and either calls the right tool
or correctly declines to call one.

**It scores 98% (47/48 checks) on an 8-scenario tool-calling benchmark, up from 40% for the
base model.**

The model is published and runnable right now:

```bash
ollama pull vasuverma/echo-v4.7
ollama run vasuverma/echo-v4.7
```

> **This is the `master` branch** — the Echo model: fine-tuning, evaluation, and deployment.
> The [`main`](https://github.com/VasuVerma123/mlops_finetuning/tree/main) branch is a
> separate, general-purpose MLOps fine-tuning hub (Streamlit UI, MLflow tracking, QLoRA
> training for any model). The two branches do not share code.

## Results

| Model | Accuracy | Checks passed |
|---|---:|---:|
| **V4.7-AWS (published)** | **98%** | **47 / 48** |
| V4.6-AWS | 90% | 43 / 48 |
| V4.2 (`think=True`) | 85% | — |
| V4.5 | 77% | — |
| V4 | 73% | — |
| Qwen3-4B base (no fine-tuning) | 40% | — |

The benchmark is 8 scenarios worth 48 individual checks in total. Here is where V4.6
stood, and what V4.7 was built to fix:

| # | Scenario | What is tested | Checks | V4.6 |
|---|---|---|---:|---:|
| 1 | Direct Booking | Calls `book_appointment` with all four params | 7 | 100% |
| 2 | Availability | Calls `check_availability`, does not book | 7 | 100% |
| 3 | Cancellation | Calls `cancel_appointment` | 7 | 100% |
| 4 | FAQ | Answers in plain text, calls **no** tool | 5 | 100% |
| 5 | Conflict | Declines a booked slot *and* offers alternatives | 5 | 100% |
| 6 | Privacy | Will not name who holds a slot | 5 | 100% |
| 7 | **Reschedule** | Calls `reschedule_appointment`, **not** `cancel` | 6 | **67%** |
| 8 | **Distractor** | Refuses off-topic, **never** calls `get_weather` | 6 | **50%** |

V4.6 lost exactly 5 of 48 checks, all in those last two rows: 2 on Reschedule (it reached
for `cancel_appointment`) and 3 on Distractor (it reached for `get_weather` instead of
declining). V4.7 was trained surgically on those two failures — 40 reschedule and 35
distractor examples — and recovered 4 of the 5, landing at 47/48.

> **Caveat, stated plainly:** the per-scenario split for V4.7 is not recorded in this
> repository, only the 47/48 total. Re-run `aws_eval_v4_7.py` to see which single check
> still fails; the script now writes a `failed_checks` list per scenario into its results
> JSON. The V4.6 and V4.2 per-scenario figures above are the baselines hard-coded in
> `aws_eval_v4_7.py`.

Full methodology, scoring rules, and training recipes: **[RESULTS.md](RESULTS.md)**.

## What the model actually does

Echo is given a system prompt describing Dr. Maya Chen (a fictional therapist), her working
hours, her cancellation policy, and six tools. On each turn it produces:

1. a reasoning block in `<think>...</think>`, then
2. either a `<tool_call>{...}</tool_call>` JSON block, or a plain-text reply.

```
User:  "Can we move my 2 PM appointment on March 24th to 3 PM instead?"

Echo:  <think>The client wants to move an existing appointment, not cancel it.
       That's reschedule_appointment, with old and new time slots.</think>
       <tool_call>{"name": "reschedule_appointment", "arguments": {
         "date": "2026-03-24", "old_time_slot": "2:00 PM",
         "new_time_slot": "3:00 PM", "client_name": "Anika Patel"}}</tool_call>
```

The six tools are `check_availability`, `book_appointment`, `cancel_appointment`,
`reschedule_appointment`, `send_message`, and `get_weather`. The last one is a deliberate
**distractor** — it exists only so the benchmark can check the model *doesn't* reach for it.

> All names and calendar data — Dr. Maya Chen, Sarah Kim, Anika Patel, Tom Wilson — are
> synthetic, generated by the training scripts. No real person's data is in this repository.

## Model card

| Property | Value |
|---|---|
| Base model | `Qwen/Qwen3-4B` |
| Method | LoRA (PEFT) via SFT, two stacked adapters |
| Stack | Qwen3-4B → merge V4.6 → V4.7 LoRA |
| Training hardware | AWS `g5.2xlarge` (A10G, 24 GB) |
| Precision | bf16 (no quantization during training) |
| Adapter size | ~126 MB each |
| Quantization (serving) | Q8_0 GGUF, ~4.3 GB |
| Context length | 4096 tokens |
| Inference | `temperature=0.3`, `top_p=0.9`, `repeat_penalty=1.1`, thinking enabled |
| Published at | <https://ollama.com/vasuverma/echo-v4.7> |

## Reproducing the benchmark

You need the two LoRA adapters and a GPU with ~16 GB of VRAM.

```bash
pip install torch transformers peft accelerate

export ECHO_V46_ADAPTER=/path/to/final_v4.6
export ECHO_V47_ADAPTER=/path/to/final_v4.7
export ECHO_EVAL_RESULTS=eval_v47_results.json

python aws_eval_v4_7.py
```

The script loads the base model, merges V4.6, stacks V4.7 on top, runs all 8 scenarios,
prints a per-check pass/fail table, and writes `eval_v47_results.json` containing the
accuracy, the per-scenario scores, the names of any failed checks, and the raw model
responses.

To retrain from scratch, run `aws_finetune_v4_6.py` then `aws_finetune_v4_7.py` — both
generate their own synthetic datasets, so no data files are needed.

## Known limitations

- **One benchmark, 8 scenarios, 48 checks.** It is a focused smoke test of tool-selection
  behaviour, not a broad capability evaluation. 98% means 47 of those 48 checks, nothing more.
- **Scoring is keyword- and JSON-shape-based**, not model-graded. A correct answer phrased
  unusually can be scored as a miss (e.g. the conflict scenario looks for words like
  "unavailable" or "instead").
- **Single-turn.** Every benchmark scenario is one incoming message. Multi-turn behaviour
  is exercised by `ollama_test.py` and `streamlit_echo.py` but is not scored.
- **The tools are simulated.** `streamlit_echo.py` mutates an in-memory calendar; nothing
  touches a real calendar, inbox, or phone.
- **One persona.** Echo is tuned hard on Dr. Maya Chen's rules. It is not a general
  scheduling model and will carry her working hours and policies into other contexts.
